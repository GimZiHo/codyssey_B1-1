# 기능 통합 검증으로 상태 전환과 실제 결함 확인하기

## 1. 학습 목적

기능을 하나씩 만들 때는 그 기능만 확인했다. 제출 전에는 사용자가 실제로 하는 순서대로 기능을 이어서 실행하고, 여러 상태가 함께 바뀔 때도 화면이 의도한 결과로 남는지 확인해야 한다. 이 문서는 통합 검증에서 무엇을 이어서 보는지, 그리고 검증이 실패했을 때 **기대값이 틀린 것**과 **실제 결함**을 어떻게 가르는지 기록한다.

## 2. 핵심 개념

### 개별 검증과 통합 검증의 차이

개별 검증은 하나의 상태 변화만 본다. 예를 들어 테마 버튼을 누르면 `data-theme`이 `dark`가 되는지 확인한다. 통합 검증은 여러 기능을 한 흐름으로 이어서 실행하고, 기능들이 **공유하는 것**이 어긋나지 않는지 본다. 이 페이지에서 공유되는 것은 DOM 트리, CSS 변수, 스크롤 위치, 그리고 문서 전체 높이다.

한 화면이 동시에 들고 있는 상태는 다음과 같다.

| 상태 | 저장되는 곳 | 화면에 반영되는 방법 |
| --- | --- | --- |
| 테마 | `html`의 `data-theme`, `localStorage` | `[data-theme="dark"]`의 CSS 변수 값 |
| 메뉴 열림 | `#navigation-menu`의 `active` 클래스 | `nav.menu-ready ul.active { display: flex }` |
| 스크롤 위치 | `window.scrollY` | `nav.scrolled`, `#scroll-top`의 `hidden` |
| 요청 상태 | `projectState` 객체 | `renderProjects()`가 문구·재시도 버튼·카드를 그린다 |
| 폼 검증 결과 | 각 입력의 `aria-invalid`, 오류·성공 문구 | `.field-error`, `#contact-success` |
| 등장 여부 | 섹션의 `visible` 클래스 | `main section.reveal.visible` |

### 기능이 맞닿는 경계

통합에서 문제가 생기는 자리는 대부분 다음 네 가지다.

1. **비동기 응답이 레이아웃을 바꾼다.** API 목록의 길이가 섹션 높이를 바꾸고, 섹션 높이가 등장 효과의 판단 기준을 바꾼다([Intersection Observer](014-intersection-observer.md)).
2. **시간과 순서가 끼어든다.** 응답이 늦게 오는 동안 사용자가 먼저 스크롤할 수 있다. 같은 기능도 "응답 전에 도착"과 "응답 후에 도착"에서 결과가 달라질 수 있다.
3. **공유 변수가 여러 화면 요소를 한꺼번에 바꾼다.** 테마를 바꾸면 배경뿐 아니라 카드 그림자, 폼 오류 색, 요청 실패 안내 색까지 함께 바뀐다.
4. **검증 도구도 화면을 바꾼다.** 자동화 도구의 클릭은 대상 요소를 화면 안으로 스크롤한 뒤 누른다. 스크롤 위치가 걸린 확인에서는 이 동작이 결과에 섞인다.

### 실패를 가르는 기준

검증이 실패로 나오면 원인은 셋 중 하나다.

- **도구나 검증 코드가 만든 부작용** — 확인 방법을 고친다.
- **기대값이 화면의 실제 모습과 다름** — 기대값을 고친다.
- **실제 결함** — 코드를 고친다.

세 가지를 구분하려면 참·거짓만 남기지 말고 **화면의 실제 값**을 함께 기록해야 한다. 이 프로젝트에서는 요소 높이, 화면에 걸친 높이, 뷰포트 높이, 교차 비율, 스크롤 위치를 같이 남겼고, 그 값들이 그대로 판단 근거가 되었다.

## 3. 프로젝트 적용

확인한 흐름은 두 종류다.

- **통합 흐름**: 모바일 375×667, 태블릿 768×1024, 데스크톱 1280×800에서 메뉴 이동 → 스크롤·등장 → 테마 전환 → API 목록 → 폼 제출 → 맨 위로 → 새로고침을 한 번에 이어서 실행했다.
- **경계**: 응답 3초 지연, 저장소 30건·100건의 긴 목록, 403 실패 뒤 테마 전환과 재시도.

API는 실제 호출 대신 **2026-09-15에 실제로 받은 응답(저장소 3건)** 을 그대로 돌려주도록 가로채 확인했다. 비인증 GitHub API는 시간당 60회 제한이 있어([fetch·async/await와 요청 상태 렌더링](018-async-fetch-states.md)) 반복 실행에 적합하지 않고, 응답이 매번 같아야 화면 결과를 비교할 수 있기 때문이다. 목록 길이를 바꾸는 확인에는 같은 형태의 가짜 목록을 만들어 썼다.

## 4. 실행 흐름

모바일에서 한 번의 통합 흐름이 만드는 상태 전환이다. 괄호 안은 해당 기능의 학습 기록이다.

1. 햄버거 버튼 클릭 → `classList.toggle('active')` → CSS가 메뉴를 펼친다([009](009-menu-click-event.md)).
2. 메뉴의 "프로젝트" 링크 클릭 → 앵커 이동이 `scroll-behavior: smooth`로 진행된다([002](002-anchor-links.md), [010](010-smooth-scrolling.md)).
3. 스크롤이 움직이며 `scroll` 이벤트가 연달아 발생 → 60px에서 `nav.scrolled`, 300px에서 맨 위로 버튼 표시([011](011-scroll-event.md), [012](012-conditional-class-toggle.md)).
4. 섹션 제목이 화면에 20% 들어옴 → Observer 콜백 → 섹션에 `visible`([014](014-intersection-observer.md)).
5. 테마 버튼 클릭 → `dataset.theme`과 `localStorage` 저장 → CSS 변수가 바뀌며 배경·카드 그림자·오류/성공 문구 색이 함께 바뀐다([005](005-theme-attribute-selector.md), [013](013-local-storage-theme.md)).
6. 문의 폼 빈 제출 → 필드별 오류와 첫 오류 필드 포커스, 성공 안내 해제 → 값을 채워 다시 제출 → 성공 안내([016](016-form-validation.md), [017](017-form-success-state.md)).
7. 맨 위로 버튼 클릭 → `window.scrollTo` → 버튼이 숨고 `nav` 배경이 되돌아온다.
8. 새로고침 → `localStorage`에서 테마 복원, `fetch`가 다시 나가 로딩 → 카드 표시([018](018-async-fetch-states.md)).

통합 검증에서는 각 단계의 결과뿐 아니라 **앞 단계의 상태가 남아 있는지**를 함께 본다. 테마를 바꾼 뒤에도 카드가 그대로인지, 폼을 제출한 뒤에도 테마가 `dark`인지, 새로고침 뒤에는 테마만 남고 폼과 메뉴는 초기 상태로 돌아가는지가 그 예다.

## 5. 확인 방법과 결과

Ubuntu 24.04, Node.js 24.18.1, Playwright 1.63.0, Chromium 153.0.8010.12 헤드리스 셸에서 임시 HTTP 서버로 `src/`를 열어 확인했다. **최신 정식 Chrome에서의 확인은 아직 하지 않았다.** 검증 스크립트와 실행 기록은 `/tmp/portfolio-integration-20260916/`에 있다(`verify-integration.cjs`, `result.log`, `verify-reveal-title.cjs`, `result-reveal-title.log`, `NOTES.md`).

### 통합 흐름과 경계 (2026-09-16, 등장 효과를 고치기 전 코드)

세 화면 크기의 통합 흐름은 대부분 기대한 대로였다. 로딩 문구에서 카드로 바뀐 뒤 메뉴 이동·테마 전환·폼 제출을 이어서 해도 앞 단계의 상태가 유지됐고, 응답이 3초 늦게 와도 로딩 중 등장한 섹션과 스크롤 위치가 그대로 남았으며, 403 실패 화면에서 테마를 바꾸면 실패 안내 색이 다크 테마 값으로 바뀌고 재시도로 카드가 채워졌다.

실패로 나온 세 건은 아래와 같이 갈렸다.

| 실패로 나온 항목 | 함께 기록한 실제 값 | 판단과 처리 |
| --- | --- | --- |
| 테마 전환 뒤 스크롤 위치 유지 | 위치가 페이지 위쪽으로 이동 | **도구의 부작용.** 자동화 도구의 클릭이 페이지 맨 위의 `nav`를 화면 안으로 스크롤했다. DOM에서 직접 클릭하도록 확인 방법을 바꾸자 위치가 유지됐다 |
| 태블릿 첫 화면에서 `#projects`가 이미 등장 | 첫 화면에 230px 노출(화면 높이의 22.5%) | **기대값이 틀림.** 화면이 높아 섹션이 첫 화면에 실제로 걸쳐 있었다. 기대값을 실측 기하에 맞췄다 |
| 모바일에서 저장소 30건일 때 `#projects`가 `opacity: 0` | 섹션 6,827px(뷰포트의 10배), 최대 교차 비율 `0.093`, 콜백은 최초 알림 한 번뿐 | **실제 결함.** 목록이 길어질수록 등장 조건을 만족할 수 없는 구조였다 |

세 번째 항목은 개별 기능 검증에서는 드러나지 않았다. 저장소가 3건일 때는 섹션이 화면 높이의 1.1배라 문제가 없었고, 기능을 함께 실행하면서 목록 길이를 바꿔 본 뒤에야 나타났다.

### 보완과 최종 코드 확인 (2026-09-16)

첫 보완안은 등장 조건에 "화면의 20%를 채웠는가"를 더하고 임계값 목록을 낮추는 방식이었다. 코드 검토에서 섹션이 뷰포트의 20배를 넘으면 같은 문제가 남고 기준도 복잡해진다는 점이 드러나 채택하지 않았다. 최종 보완은 관찰 대상을 섹션에서 **제목**으로 바꾸는 방식이다([014](014-intersection-observer.md)).

최종 코드에서는 바뀐 등장 로직에 직접 관계된 세 경로만 375×667에서 확인했고, 모두 기대한 대로였다.

- 짧은 섹션(`#contact`, 540px): 제목이 11% 보일 때는 대기, 20% 이상에서 등장.
- 저장소 100건으로 섹션이 22,658px(뷰포트의 34배)이 되고 화면 진입 전에 응답이 끝난 경우: 맨 위에서는 대기, 제목 진입으로 등장.
- 제목이 등장한 뒤 2초 지연 응답이 도착해 섹션이 100px에서 22,658px로 늘어난 경우: 표시 상태가 그대로 유지.

위 통합 흐름 결과는 **보완 전 코드에서 얻은 것**이고, 최종 코드에서는 등장 로직 세 경로만 다시 확인했다. 두 결과를 구분해 읽어야 한다.
