# Live Server로 로컬 개발 서버 실행하기

## 1. 학습 목적

지금까지는 파일을 만들고 브라우저로 열어 확인했다. 과제 1장은 **VS Code와 Live Server로 개발 환경을 구성**하도록 요구한다. 이 문서는 로컬 개발 서버가 무엇을 해 주는지, 워크스페이스 루트가 URL 경로로 어떻게 바뀌는지, 저장 후 자동 새로고침이 어떤 구조로 일어나는지를 이 프로젝트의 `src/index.html` 경로와 이어서 기록한다.

## 2. 핵심 개념

### 로컬 개발 서버

**Live Server**는 VS Code 확장(확장 ID `ritwickdey.liveserver`)이다. 확장을 실행하면 VS Code의 **확장 호스트**(확장 코드를 실행하는 별도 프로세스) 안에서 작은 HTTP 서버가 뜨고, 워크스페이스의 파일을 HTTP 응답으로 내보낸다. 브라우저 주소가 `file:///...`에서 `http://127.0.0.1:5500/...`으로 바뀐다는 뜻이다.

- `file://`: 브라우저가 디스크의 파일을 직접 읽는다. 출처(origin)가 파일 경로다.
- `http://`: 브라우저가 서버에 요청을 보내고 응답을 받는다. 출처가 호스트와 포트(`127.0.0.1:5500`)로 정해지고, 상태 코드(200·404)와 응답 헤더가 생긴다.

배포된 페이지는 언제나 HTTP로 서비스되므로, 개발 중에도 같은 방식으로 확인하는 편이 실제 동작에 가깝다.

### 워크스페이스 루트와 URL 경로

서버는 **문서 루트**(URL의 `/`에 대응하는 디렉터리)를 하나 정해 두고 요청 경로를 그 아래 파일로 찾는다. 별도 설정이 없으면 Live Server의 문서 루트는 **VS Code에서 연 워크스페이스 폴더**다. 이 프로젝트의 소스는 `src/` 아래에 있으므로([AGENTS.md](../../AGENTS.md)의 프로젝트 공통 조건) 경로 대응은 다음과 같다.

| 요청 URL | 찾는 파일 | 결과 |
| --- | --- | --- |
| `/src/index.html` | `src/index.html` | 200 |
| `/index.html` | 워크스페이스 루트의 `index.html` | 404 (그 자리에 파일이 없다) |

`/index.html`의 404는 설정 오류가 아니라 **문서 루트가 저장소 루트이고 거기에는 `index.html`이 없다**는 사실을 그대로 보여 주는 결과다.

HTML 안의 상대 경로도 같은 규칙으로 해석된다. `src/index.html`이 `css/style.css`, `js/main.js`, `images/…`를 상대 경로로 참조하므로([HTML에 외부 CSS와 JavaScript 연결하기](003-external-css-javascript.md)), 브라우저는 현재 문서 경로 `/src/index.html`을 기준으로 `/src/css/style.css`, `/src/js/main.js`를 이어서 요청한다.

### 저장 후 자동 새로고침

Live Server는 HTML을 그대로 내보내지 않고, 응답 본문에 **라이브 리로드용 스크립트를 끼워 넣어** 보낸다. 이 스크립트가 브라우저에서 실행되면 서버와 **WebSocket**(한 번 연결해 두고 양쪽이 서로 메시지를 보낼 수 있는 통신 방식)으로 연결된다. 파일을 저장하면 서버가 변경을 감지해 연결된 브라우저에 알리고, 스크립트가 페이지를 새로 읽는다. 브라우저에서 새로고침 키를 누르지 않아도 화면이 갱신되는 이유다.

즉 자동 새로고침은 HTML 원본이 아니라 **서버가 응답에 덧붙인 스크립트**가 만든다. 원본 `src/index.html`에는 이 스크립트가 없고, 배포본에도 들어가지 않는다.

## 3. 프로젝트 적용

- 워크스페이스: `/home/jiho/projects/academy/codyssey_B1-1` (WSL Ubuntu에서 연 폴더)
- 서버 주소: `0.0.0.0:5500`에서 연결을 받는다. 루프백(`127.0.0.1`)뿐 아니라 다른 네트워크 인터페이스의 접속도 받는 설정이다.
- 확인할 페이지: `http://127.0.0.1:5500/src/index.html`
- 설정 파일: 저장소에 `.vscode` 디렉터리가 없다. 포트 5500과 문서 루트는 모두 확장의 기본값이다.
- 소스 변경: 없다. 이번 단계는 환경 확인만 한다.

## 4. 실행 흐름

1. VS Code에서 워크스페이스 폴더를 연다(WSL 창).
2. `src/index.html`을 열고 우클릭 → **Open with Live Server**, 또는 상태 표시줄의 **Go Live**를 누른다.
3. 확장 호스트 안에서 HTTP 서버가 뜨고 5500 포트에서 연결을 기다린다.
4. 브라우저가 `GET /src/index.html`을 보낸다 → 서버가 워크스페이스 루트 기준으로 파일을 찾아 200으로 응답한다.
5. 응답 본문에는 라이브 리로드 스크립트가 덧붙어 있다 → 브라우저가 이 스크립트를 실행해 서버와 WebSocket으로 연결한다.
6. 브라우저가 이어서 `/src/css/style.css`, `/src/js/main.js`, 이미지 등을 요청한다.
7. 편집기에서 파일을 저장한다 → 서버가 변경을 감지해 WebSocket으로 알린다 → 페이지가 다시 로드된다.

## 5. 확인 방법과 결과

환경: VS Code 1.137.0, WSL Ubuntu, 확장 `ritwickdey.liveserver` 5.7.10.

확인한 것

- 확장이 WSL 쪽에 설치되어 있다(5.7.10).
- VS Code 확장 호스트 프로세스가 `0.0.0.0:5500`에서 LISTEN 상태다.
- `GET /src/index.html` → **200**, 응답 본문 끝에 라이브 리로드용 WebSocket 스크립트가 주입되어 있다.
- `GET /index.html` → **404**. 워크스페이스 루트에 `index.html`이 없어서 나오는 정상 결과다.
- 저장소에 `.vscode` 설정이 없어 포트·문서 루트는 기본값이다.

### 렌더링과 자동 새로고침 확인 (2026-09-19)

위 두 항목은 2026-09-19에 확인을 마쳤다.

- **실제 브라우저에서 페이지가 표시되는지.** `src/tests/live-server-check.cjs`로 확인했다. 첫 실행은 9 통과 / 1 실패였고, 실패는 API 응답 대기를 두지 않아 생긴 것이었다. 이 1건만 `src/tests/live-api-recheck.cjs`로 재검증해 실제 `api.github.com` 호출이 HTTP 200으로 응답하고 카드 3건이 그려지는 것을 확인했다.
- **파일 저장 시 자동 새로고침이 실제로 일어나는지.** 같은 재검증에서 확인했다. 주입된 WebSocket 스크립트가 실제로 페이지를 다시 불러오는 것까지 확인 완료다.

두 항목 모두 사람이 직접 조작하며 보는 확인은 하지 않았다. 관련 근거는 [019](019-integration-verification.md)의 "남은 확인 반영" 절에도 함께 남겼다.

사용자가 직접 확인하는 절차

1. VS Code에서 `src/index.html`을 열고 **Go Live**를 누른다.
2. 브라우저에서 `http://127.0.0.1:5500/src/index.html`을 연다. 포트폴리오 화면이 보이면 서버와 상대 경로 연결이 정상이다.
3. 브라우저 창을 옆에 둔 채 `src/index.html`의 문구를 조금 바꾸고 저장한다. 손대지 않아도 화면이 갱신되면 자동 새로고침이 동작하는 것이다.
4. 주소를 `http://127.0.0.1:5500/`로 바꾸면 워크스페이스 루트의 파일 목록이나 404가 나온다. 문서 루트가 저장소 루트라는 뜻이며, 확인용 주소에는 `/src/`를 포함해야 한다.
